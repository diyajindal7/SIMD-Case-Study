Steps 6–7: Workload Testing, Performance Measurement and Visualization

6. Testing with Different Workloads and Processing Resources

After implementing the sequential, parallel and SIMD-oriented versions of the numerical computation, performance testing is performed to determine how execution time changes for different workload sizes and processing configurations.

The computation used throughout the case study is:

B[i] = A[i]^2 + 2A[i] + 1

or, equivalently:

B[i] = A[i] × A[i] + 2 × A[i] + 1

Each array element is processed independently, making the computation suitable for vector-oriented SIMD execution.

6.3 Repeated Measurements

Execution time can vary because of operating-system scheduling, background applications, CPU frequency changes, caching and other system activity.

Therefore, each configuration is executed multiple times.

The benchmark uses:

7 runs per configuration

The mean execution time is calculated from the repeated measurements and is used for the main performance comparison.

Using repeated measurements provides a more reliable estimate than relying on a single execution.

7. Performance Measurement

7.1 Timing Method

The benchmark uses OpenMP's wall-clock timer:

double start = omp_get_wtime();

/* computation */

double end = omp_get_wtime();

The execution time is calculated as:

Execution Time = end - start

The same timing method is used for the sequential, SIMD and parallel measurements in the Member 3 benchmark so that the results are directly comparable.

Important: The original sequential implementation used clock(), while the OpenMP implementation used omp_get_wtime(). For the final Member 3 comparison, all measurements are collected again using omp_get_wtime() to maintain a consistent wall-clock measurement method.

7.2 Correctness Verification

Performance measurements are meaningful only when all implementations produce the same correct result.

The benchmark therefore checks the computed output values.

For:

A[0] = 0

the expected result is:

B[0] = 1.000000

For:

N = 10,000,000

the final input value is:

A[9,999,999] = 9999.999

and the corresponding result is:

B[9,999,999] = 100019980.998001

The benchmark performs correctness checks after the computation. A configuration is considered valid only when the expected output is produced.

7.4 Average Execution Time

For every configuration, seven execution times are collected.

The average execution time is calculated as:

T_avg = (T_1 + T_2 + ... + T_n) / n

where:

T_i is the execution time of an individual run.

n is the number of runs.

In this experiment:

n = 7

The average is used for the main performance analysis.

The minimum, maximum and standard deviation of the measurements are also retained to understand variation between runs.

7.5 Speedup

Speedup measures how much faster an implementation is compared with the sequential baseline.

For SIMD:

Speedup_SIMD = T_Sequential / T_SIMD

For parallel execution:

Speedup_Parallel = T_Sequential / T_Parallel

For example, if the sequential implementation requires 2 seconds and the SIMD implementation requires 1 second:

Speedup = 2 / 1 = 2

This represents a 2× speedup.

The actual values used in the final report are obtained from the experimental dataset.

7.6 Parallel Efficiency

For the parallel implementations, efficiency is calculated as:

Efficiency = Speedup / Number of Threads

For example, if a four-thread execution achieves a speedup of 3.2:

Efficiency = 3.2 / 4 = 0.8 = 80%

Efficiency helps determine whether increasing the number of threads results in proportional performance improvement.

7.7 SIMD Performance Advantage

The primary objective of the case study is to determine whether SIMD provides a significant performance advantage.

SIMD speedup is calculated as:

SIMD Speedup = T_Sequential / T_SIMD

The percentage reduction in execution time is calculated as:

SIMD Advantage (%) =
((T_Sequential - T_SIMD) / T_Sequential) × 100

A project-defined threshold of:

SIMD Speedup >= 1.5

is initially used to classify SIMD as providing a significant performance advantage.

Therefore:

SIMD Speedup >= 1.5
        ↓
SIMD Significant = 1

and:

SIMD Speedup < 1.5
        ↓
SIMD Significant = 0

The 1.5× threshold is a project-defined criterion, not a universal definition of SIMD significance. The threshold is explicitly documented so that the AI classification rule is reproducible.

11. Performance Observations

The benchmark is designed to answer the following questions:

How does execution time change as the data size increases?

Does SIMD reduce execution time compared with the sequential implementation?

Does SIMD speedup increase for larger workloads?

How does increasing the number of OpenMP threads affect execution time?

How do static, dynamic and guided scheduling compare?

At what workload size does SIMD reach the project-defined significant-speedup threshold?

Does increasing the number of threads continue to provide proportional speedup?

The conclusions are based on the measured results rather than assuming that one implementation will always be faster.

12. Preparation of AI Dataset

The performance measurements generated during Steps 6–7 provide the experimental evidence required for the AI stage.

The AI model developed by Member 4 will use workload characteristics to predict whether SIMD is likely to provide a significant performance advantage.

The measured SIMD performance is used to generate the ground-truth target:

simd_significant

where:

1 → SIMD speedup >= 1.5
0 → SIMD speedup < 1.5

Important Data-Leakage Consideration

Measured SIMD execution time and measured SIMD speedup should not be used as input features when the goal is to predict whether SIMD should be selected before execution.

Those values are available only after running the SIMD implementation.

Instead, the AI model should use characteristics available before execution, such as:

Data size
Data type
Operation type
Operation complexity
Memory footprint
Available processing resources

The measured benchmark outcome provides the target label.

Therefore, the workflow becomes:

Workload characteristics
        ↓
AI model
        ↓
Predict SIMD significance
        ↓
Choose execution strategy
        ↓
Run Sequential / SIMD / Parallel SIMD

14. Conclusion

Steps 6–7 provide the experimental and analytical part of the SIMD-oriented data-processing case study.

The benchmark evaluates sequential, SIMD and parallel implementations across multiple workload sizes and thread configurations. Repeated measurements are collected using a consistent wall-clock timing method to reduce the effect of individual noisy runs.

Execution time, speedup, efficiency and SIMD performance advantage are calculated from the measured data. Visualizations are generated to show how workload size, SIMD execution and OpenMP scheduling affect performance.

The results from this stage provide the empirical dataset required for the AI component of the project. Member 4 can use these measurements to construct labels indicating whether SIMD provides a significant performance advantage and subsequently develop an AI-based execution-strategy selector.

The final conclusions about SIMD performance are based on the actual measurements obtained from the target system rather than predetermined performance assumptions.
